Errors and rate limits

What does each Live Tennis API error mean, and when should a client retry? Every error is JSON with a stable error code. Retry a per-minute 429 and any 5xx, waiting Retry-After when it is sent. Fix the request on a 400, the key on a 401 and the plan on a 403. The daily-quota 429 and abuse_throttled are never retried.

Status codes and error codes are read from the OpenAPI spec when the page is built. Retry rules checked against livetennisapi 1.8.0 for Python and 1.10.2 for JS on 2026-11-09.

What does an error response look like?

Every error is JSON. Most use the Error schema:

  • error: a stable machine-readable code. Branch on this, never on the text.
  • detail: a human-readable explanation, when one adds anything.
  • allowed: on a refused enumerated parameter, the values that would have been accepted.

Two other shapes exist. A 410 carries MatchMerged or PlayerMerged: error: "merged", merged_into, merged_at and detail. A 404 on /players/{playerId} and its stoppage and injury routes carries PlayerNotFound. It adds detail and see when the id belongs to the results archive. Some codes add their own fields, named in the tables below.

401 or 403: is it the key or the plan?

A 401 means the key itself failed: it is missing, unknown or disabled. Send it as Authorization: Bearer <key>, X-API-Key: <key> or ?token=<key>. A 403 means the key works and the plan stops short of the data. It is never a silent empty result.

Two 404s carry no code of their own. GET /matches/{matchId}/score answers 404 for an unknown match or an upcoming match with no score yet. It does the same for a cancelled match that was never played, and for a settled match with nothing recorded.

The archive tape answers a plain 404 for a result from 1968 to 2012. So does a 2013 to 2022 result that was never reconstructed, or one whose reconstruction did not prove its binding. The three are not told apart.

A 410 is only ever about an id that once existed. An id that was never issued stays a 404.

What does a 429 mean, and when do I retry it?

Every 429 carries a Retry-After header. The body tells you which of three limits you hit, and only the first is worth retrying.

  1. Per-minute window. error: "rate_limited" with no scope. The body names the next tier up in upgrade_url, tier and price. Wait Retry-After seconds and send the request again.
  2. Daily quota. error: "rate_limited" with scope: "day", limit_per_day and resets_at, the ISO instant the daily window resets. Do not retry. Stop until resets_at, or upgrade.
  3. Abuse throttle. error: "abuse_throttled" with retry_at_epoch. A 24-hour block for a client that keeps calling far past its cap. A retry loop that backs off never sees it. Fix the loop and wait until retry_at_epoch.

How do the official clients retry?

The Python client (1.8.0) and the JS client (1.10.2) follow the same rules. We read both from source and ran them against a local server on 2026-11-09.

What the official clients retry
The API answersRetriedHow
429 rate_limited, per-minute windowYesWaits Retry-After if sent, else exponential backoff
Any 5xxYesWaits Retry-After if sent, else exponential backoff
Connection error or timeoutYesExponential backoff
429 rate_limited with scope: "day"NoRaises at once
429 abuse_throttledNoRaises at once
400, 401, 403, 404 and every other 4xxNoRaises at once
  • Up to 2 retries by default, so 3 attempts in all. Set max_retries in Python or maxRetries in JS. 0 turns retries off.
  • With Retry-After, the wait is that many seconds, at most 60.
  • Without it, the wait is 0.5 s doubled on each attempt plus up to 0.25 s of random jitter, at most 10 s. The jitter keeps many clients from retrying in step.
  • When the retries run out, the client raises the error for the last answer.

How should my own client back off?

Do what the official clients do. Retry a 429 only when the body has no scope: "day" and the code is not abuse_throttled. Retry a 5xx or a dropped connection. Wait Retry-After when it is sent, and otherwise back off exponentially with jitter. Cap the number of retries. Never retry a 400, 401, 403, 404, 409 or 410 unchanged.

GET /usage returns your plan, your limits and today's calls, and calling it never uses quota. Refused requests do not spend the daily allowance, so remaining_day does not fall on a 429, 403 or 404. The per-minute window is on the X-RateLimit-* headers of every response. Plans and prices are on the pricing page.
